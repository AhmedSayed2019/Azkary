# patches/

`quran_library-4.2.1-customizations.patch` captures every change made to
the vendored `libraries/quran_library-4.2.1` package (a local `path:`
dependency in `pubspec.yaml`) since it was first vendored in commit
`995989f` ("Upgrade quran_library from 2.2.3+1 to 4.2.1"). It does **not**
include `pubspec.lock` — that's regenerated by `flutter pub get`, never
patched.

## Why this exists

`quran_library` is vendored as source (not a pub.dev version pin), and
we've edited its source directly (new "all features" bottom sheet, ayah
repeat sheet with a searchable surah picker and +/- steppers, a fixed
repeat-count off-by-one bug, a menu icon in the Quran top bar, etc.).
Because it's edited in place, pulling a fresh copy of the package (a new
version, or re-syncing with upstream) would silently discard all of this
unless it's captured separately — hence this patch.

## How to update the package while keeping these customizations

1. **Regenerate the patch first if you've made further edits** (skip if
   `patches/quran_library-4.2.1-customizations.patch` is already current):
   ```bash
   git diff 995989f..HEAD -- libraries/quran_library-4.2.1 \
     ':!libraries/quran_library-4.2.1/pubspec.lock' \
     ':!libraries/quran_library-4.2.1/example/pubspec.lock' \
     > patches/quran_library-4.2.1-customizations.patch
   ```

2. **Get the new package source** into a fresh folder, e.g.
   `libraries/quran_library-<new-version>/` (download from pub.dev, or
   `git clone` the upstream repo at the new tag).

3. **Try applying the patch to the new folder.** Since the patch's paths
   are hardcoded to `quran_library-4.2.1/`, either:
   - rename the new folder to `quran_library-4.2.1/` temporarily before
     applying, then rename it back to the real version afterward, or
   - use `git apply -p1 --directory=libraries/quran_library-<new-version>`
     after stripping the old version segment with `sed`, or simplest:
     copy the new version's files *into* the existing
     `quran_library-4.2.1/` folder (overwriting everything except our
     changed files) and just bump the version string inside
     `pubspec.yaml`/`CHANGELOG` manually.

   ```bash
   git apply --check patches/quran_library-4.2.1-customizations.patch
   git apply patches/quran_library-4.2.1-customizations.patch
   ```

4. **Resolve conflicts.** If upstream changed the same files we touched
   (`quran_top_bar.dart` is the most likely conflict point — it's a
   heavily-modified file), `git apply` will fail on those hunks. Open the
   `.rej` files it leaves behind and manually re-apply the conflicting
   hunks against the new source.

5. **Re-run `flutter pub get`** in both the package and the app to
   regenerate `pubspec.lock` — never hand-edit or patch lock files.

6. **Re-run `flutter analyze`** on the package to confirm nothing broke,
   then do a full hot **restart** (not hot reload) before testing in the
   app — this package makes heavy use of `part`/`part of` files, and Dart
   hot reload does not reliably handle structural changes to those.

## Regenerating the patch after future customizations

Whenever you make further hand-edits to `libraries/quran_library-4.2.1`,
re-run the `git diff` command from step 1 above and commit the updated
patch file, so it always reflects the *full* current set of
customizations relative to the original 4.2.1 vendoring — not just the
latest edit.
